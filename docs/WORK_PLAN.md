# Cafe Admin 무료 클라우드 전환 작업 계획서

- 버전: 0.1
- 작성일: 2026-10-07
- 상태: W01–W03 첫 구현 완료, W04부터 미착수 (2026-10-08)
- 기준 문서: [Cafe Admin PRD](https://github.com/a01094864335-cell/cafe-admin/blob/main/docs/PRD.md)
- 대상: 개발 담당자, 서비스 운영자, 파일럿 참여자

## 1 작업 목표

기존 단일 HTML 기반 개인용 장부를 Cloudflare Workers와 D1 기반 공유 서비스로 전환한다. 사용자는 여러 카페에 참여할 수 있고, 카페에는 여러 사용자가 참여할 수 있다. 접근 권한은 카페별 멤버십에서 결정한다.

첫 구현 목표는 **두 사용자가 두 카페에 서로 다른 권한으로 참여하고 매출 한 건을 안전하게 공유하는 흐름**이다. 이 흐름으로 인증·데이터 격리·저장 방식이 검증된 다음 나머지 장부 기능을 옮긴다.

이 문서는 앞으로 수행할 작업과 검증 기준을 정의한다. 체크박스는 구현 및 검증 결과가 확보된 뒤 완료로 변경한다.

## 2 범위와 기본 결정

| 영역 | 작업 기준 |
| --- | --- |
| 화면 | 기존 화면과 계산 동작을 최대한 보존하고 저장·통신 코드를 분리 |
| 배포 | Workers Static Assets와 API를 같은 서비스 주소로 제공 |
| 데이터 | 공유 D1 DB에 카페별 데이터를 저장하고 서버에서 접근 검증 |
| 인증 | Google 로그인과 서비스 자체 세션 |
| 관계 | 사용자와 카페의 N:N 멤버십, 카페당 소유자 1명 |
| 역할 | 소유자·관리자·직원, 세부 권한은 PRD의 권한표 적용 |
| 협업 | 활성 화면 60초 갱신, 버전 기반 충돌 감지, 중복 저장 방지 |
| 자료 이전 | 소유자가 빈 카페에 기존 JSON을 가져오기 |
| 운영 | 테스트·운영 DB 분리, 오류·사용량 확인, 백업·복구 절차 |

결제, POS·은행 연동, 이미지 업로드, 자동 이메일 발송, 오프라인 편집, 실시간 공동 편집, 여러 카페 통합 손익은 이번 작업에서 제외한다. 무료 한도 수치는 PRD를 기준으로 하되 실제 배포 전에 공식 문서에서 다시 확인한다.

## 3 역할과 준비 사항

| 담당 역할 | 책임 | 착수 준비 |
| --- | --- | --- |
| 서비스 운영자 | 역할 정책 결정, 계정 소유, 파일럿 매장 선정, 백업 실행 | Cloudflare 계정, Google OAuth 앱 관리 권한, 파일럿 사용자 목록 |
| 개발 담당자 | 코드 분석, DB·API·UI 구현, 테스트, 배포·복구 절차 작성 | GitHub 저장소 접근, 개발 도구, 테스트용 로그인 계정 |
| 파일럿 참여자 | 실제 업무 시나리오 확인, 문제 재현, 장부 합계 검증 | 카페 1~2개, 개인정보가 제거된 샘플 또는 별도 테스트 자료 |

한 사람이 여러 역할을 맡을 수 있다. 실제 이름은 착수 시 배정한다. 계정 연결 대기 중에는 로컬 코드 분석과 DB 설계를 진행한다. 비밀 키는 저장소·문서에 적지 않고 배포 환경의 비밀 설정에 보관한다.

- [ ] Cloudflare 계정과 배포 연결을 준비한다.
- [ ] 테스트·운영별 Google 로그인 콜백 주소와 OAuth 앱 설정을 준비한다.
- [ ] 소유자·관리자·직원 역할별 테스트 계정을 준비한다.
- [ ] 카페 생성 허용 대상과 파일럿 참여자를 정한다.
- [ ] 기존 장부 JSON의 개인정보를 제거한 테스트 자료를 확보한다.

## 4 일정과 선행 관계

개발자 1명 기준 22개 작업일과 3개 작업일의 버퍼를 합한 약 5주를 기본안으로 잡는다. 기존 코드의 결합도와 외부 계정 설정에 따라 PRD의 4~6주 범위에서 조정한다. 달력상의 시작일은 정하지 않았으며, 각 단계 검증이 통과되어야 다음 단계로 넘어간다.

| 단계 | 예상 작업일 | 선행 조건 | 종료 시 결과 |
| --- | --- | --- | --- |
| A 분석과 기준 확정 | 2일 | 저장소·샘플 자료 | 기존 동작 목록과 이전 규칙 |
| B 개발·배포 기반 | 3일 | A | 테스트 주소, DB, 마이그레이션, CI |
| C 로그인과 N:N 권한 | 4일 | B, OAuth 설정 | 두 사용자·두 카페 권한 검증 |
| D 공유 장부 구현 | 6일 | C | 매출·구매·비용·재고·근무·집계 |
| E 자료 이전과 운영 준비 | 4일 | D | 이전·내보내기·이력·복구 검증 |
| F 파일럿과 출시 | 3일 | E | 실제 카페 운영 확인과 출시 기록 |
| 버퍼 | 3일 | 필요 시 사용 | 결함 수정과 외부 설정 지연 대응 |

핵심 선행 관계는 A → B → C → D → E → F다. 공개 운영을 서두르기 위해 카페 간 격리나 중복 저장 검증을 생략하지 않는다. 일정이 부족하면 파일럿 시작 시점을 조정한다.

### E 자료 이전과 운영 준비

**W12 JSON 이전과 내보내기 — 개발 담당자**

- [ ] 빈 카페·소유자 여부, 파일 크기·버전·필드·참조를 검증한다.
- [ ] 항목별 건수·합계·오류 미리보기와 실행 확인을 구현한다.
- [ ] 카페별 동일 파일 중복 가져오기와 실행 중 일반 장부 쓰기를 차단한다.
- [ ] 작업을 나누어 처리하고 완료 전에는 임시 기록을 장부·집계·내보내기에 노출하지 않는다.
- [ ] 작업 중단·재시도·실패 정리와 카페별 내보내기를 구현한다.
- 완료 기준: 이전 전후 건수·합계가 일치하고 부분 실패·중복 실행을 재현해도 데이터가 오염되지 않는다.

**W13 이력과 운영 관측 — 개발 담당자**

- [ ] 장부 변경·멤버십 변경·가져오기에 작업자·카페·대상·결과를 기록한다.
- [ ] API 오류를 추적할 요청 ID를 부여하고 민감한 원문·토큰을 로그에서 제외한다.
- [ ] 요청·CPU·DB 읽기/쓰기·저장량을 확인하는 절차를 작성한다.
- [ ] 무료 한도 초과 응답에서 저장 실패를 표시하고 재시도 폭주를 막는다.
- 완료 기준: 샘플 오류를 추적하고 한도 70%·85% 도달 시 대응 담당과 조치가 문서화된다.

**W14 복구와 배포 절차 — 개발 담당자와 운영자**

- [ ] 배포 전 백업, 마이그레이션, 확인, 이전 코드로 되돌리기 절차를 작성한다.
- [ ] 코드 되돌리기와 DB 복구가 별도 작업임을 구분하고 스키마 호환성을 확인한다.
- [ ] 테스트 환경에서 DB 전체 복구와 개별 카페 복구를 연습한다.
- [ ] 개별 카페 복구는 별도 복구 환경에서 데이터를 추출해 권한·관계를 검증한 뒤 반영한다.
- [ ] 소유자의 일일 JSON 백업과 파일럿 장애 연락 절차를 준비한다.
- 산출물: `docs/operations.md`, `docs/release-checklist.md`.
- 완료 기준: 복구 후 대상 카페의 합계·멤버십이 일치하고 다른 카페가 변경되지 않는다.

### F 파일럿과 출시

**W15 종합 검증 — 개발 담당자**

- [ ] 아래 검증표의 필수 시나리오를 모두 실행한다.
- [ ] 동시 접속 10명으로 주요 조회·저장을 측정하고 느린 쿼리를 개선한다.
- [ ] 데스크톱·모바일에서 카페 전환·장부 입력·초대 수락을 확인한다.
- 산출물: `docs/test-report.md`에 대상 커밋·환경·데이터 규모·결과 기록.
- 완료 기준: 치명적 결함이 없고 주요 조회·저장 응답의 95%가 2초 이내라는 목표를 확인한다.

**W16 실제 카페 시범 운영 — 운영자와 파일럿 참여자**

- [ ] 카페 1~2개에 계정·역할을 설정하고 실제 업무 시나리오를 수행한다.
- [ ] 자료 이전 직전에 기존 장부를 백업하고 전환 이후 입력 위치를 명확히 안내한다.
- [ ] 기존·신규 장부의 기준 합계를 확인하고 이중 입력을 피한다.
- [ ] 일별 오류·사용량·장부 불일치를 확인하고 결함을 수정한다.
- 완료 기준: 입력·조회·권한·백업이 실제 업무에 맞게 동작하고 출시 체크리스트가 완료된다.

## 6 PR 분할 제안

각 PR은 적용 코드, 필요한 마이그레이션, 검증 결과, 되돌리기 영향을 포함한다. 이름과 범위는 제안이며 실제 PR은 구현 시 생성한다.

| 순서 | 제안 PR | 작업 ID | 선행 PR |
| --- | --- | --- | --- |
| 1 | 기존 동작 정리와 화면·저장 코드 분리 | W01–W03 | 없음 |
| 2 | Workers·D1·CI 기반과 초기 스키마 | W04 | 1 |
| 3 | Google 로그인과 세션 | W05 | 2 |
| 4 | 카페·멤버십·초대·권한 관리 | W06–W07 | 3 |
| 5 | 매출 공유 흐름과 데이터 격리 검증 | W08 | 4 |
| 6 | 구매·비용·재고와 원자적 저장 | W09 | 5 |
| 7 | 직원·근무·급여 | W10 | 5 |
| 8 | 기간 집계·충돌·중복 저장 처리 | W11 | 6, 7 |
| 9 | JSON 이전·내보내기 | W12 | 8 |
| 10 | 이력·운영·복구와 출시 검증 | W13–W16 | 9 |

## 7 필수 검증표

| ID | 시나리오 | 통과 기준 | 연결 작업 |
| --- | --- | --- | --- |
| T01 | 사용자 A는 카페 1 소유자, 카페 2 직원 | 동일 계정의 카페별 권한이 다르게 적용 | W06 |
| T02 | 비참여 카페·타 카페 기록 ID 직접 요청 | 목록·상세·변경·내보내기 모두 차단 | W06, W08–W12 |

| T07 | 거래 생성 재시도·중복 클릭 | 거래와 재고 이동이 한 번만 반영 | W09, W11 |

인증·격리·동시성·가져오기는 자동 통합 테스트로 검증한다. 계산 함수는 기존 샘플의 기대 결과로 확인하고, 주요 사용자 흐름은 브라우저 시나리오로 검증한다. 실제 Google 로그인 연결은 테스트 환경에서 별도 확인한다.

## 8 주요 위험과 대응

| 위험 | 확인 시점 | 대응 |
| --- | --- | --- |
| 기존 코드의 강한 결합 | A | 화면 전체 재작성 전에 저장·계산 경계를 분리하고 샘플 비교 |
| 카페 격리 누락 | C 이후 각 PR | 공통 권한 검사와 모든 API의 타 카페 접근 테스트 |
| 무료 CPU·DB 한도 부족 | B의 시범 구현, D·E | 실제 실행량 측정, 쿼리·배치 크기 조정, 확대 운영 재검토 |
| 대량 JSON의 부분 반영 | E | 임시 작업 상태·일반 쓰기 제한·완료 후 공개·재시도 검증 |
| 공유 DB 복구가 타 카페에 영향 | E | 복구 환경 분리와 개별 카페 추출·복구 연습 |
| 실제 역할 정책 변경 | A, 파일럿 전 | 권한표와 테스트를 함께 수정하고 PRD와 동기화 |
| OAuth·계정 연결 지연 | 착수 | 운영자가 설정 진행, 개발자는 로컬 분석·설계를 먼저 수행 |

한도 70%는 최적화 검토, 85%는 이용 확대 중단 또는 유료 전환 검토 기준으로 삼는다. 자동 유료 전환을 작업에 포함하지 않는다. 파일럿에서는 무료 운영의 비용 제약과 장애 시 복구 절차를 운영자가 확인한다.

## 10 첫 착수 순서

1. W01에서 기존 저장·계산 로직과 샘플 백업을 분석한다.
