# Cafe Admin 무료 클라우드 구축 PRD

다중 카페와 사용자 멤버십 기반 MVP 개발 계획

버전 0.1  |  2026년 10월 7일  |  상태 제안

개인용 카페 장부를 여러 매장과 사용자가 함께 사용하는 웹 서비스로 전환한다. 사용자와 카페를 N:N 멤버십으로 연결하고, 매장별 권한과 데이터 격리를 기반으로 무료 클라우드에서 소규모 운영을 검증한다.

## 1 제품 목표

- 한 사용자가 여러 카페에 참여하고, 한 카페에 여러 사용자가 참여한다. 같은 사용자도 카페마다 다른 역할을 가진다.
- PC와 모바일에서 동일한 장부를 조회하고 수정한다. 서버가 매장별 접근 권한을 검증한다.
- 초기에는 무료 인프라 한도 내에서 운영하고, 실측 사용량에 따라 확장한다.

초기 검증 규모는 카페 10개, 가입자 50명, 동시 접속 10명으로 가정한다. 이는 개발·테스트 기준이며 무료 운영을 보장하는 수치는 아니다.

## 2 MVP 범위

| 영역 | 포함 기능 |
| --- | --- |
| 계정과 카페 | Google 로그인, 로그아웃, 세션 만료, 카페 생성·조회·전환·설정 |
| 멤버십 | 초대, 수락, 역할 변경, 참여 해제, 소유권 이전 |
| 공유 장부 | 매출·구매·비용·재고 등록·조회·수정·삭제 |
| 근무와 급여 | 직원별 근무 기록, 기존 계산 기능 이전 |
| 조회와 협업 | 기간별 매출·비용·손익, 변경 갱신, 동시 수정 충돌 감지 |
| 데이터와 운영 | JSON 이전·내보내기, 변경 이력, 오류 확인, 백업·복구 절차 |

### 첫 버전에서 제외하는 기능

결제·구독, POS·은행 연동, 영수증 이미지와 OCR, 오프라인 편집, 실시간 공동 편집, 여러 카페 통합 손익은 제외한다. 급여 계산은 기존 기능을 유지하며 세무·노무 계산 기능을 새로 확장하지 않는다.

## 3 사용자 권한과 주요 흐름

역할은 계정 전체가 아니라 카페 멤버십에 부여한다. 예를 들어 사용자 A는 강남점의 소유자이면서 성수점의 직원일 수 있다.

| 기능 | 소유자 | 관리자 | 직원 |
| --- | --- | --- | --- |
| 매출·구매·비용·재고 관리 | 가능 | 가능 | 불가 |
| 전체 손익·급여 조회 | 가능 | 가능 | 불가 |
| 전체 근무 기록 관리 | 가능 | 가능 | 불가 |
| 본인 근무 기록 조회·입력 | 가능 | 가능 | 가능 |
| 직원 초대·참여 해제 | 가능 | 가능 | 불가 |
| 관리자 지정·해제 | 가능 | 불가 | 불가 |
| 카페 설정·데이터 내보내기 | 가능 | 불가 | 불가 |
| 소유권 이전 | 가능 | 불가 | 불가 |

카페마다 소유자 1명을 두고, 소유권 이전은 한 번의 원자적 처리로 완료한다. 소유자는 이전 없이 탈퇴할 수 없다. 관리자는 소유자나 다른 관리자의 권한을 바꿀 수 없다. 직원의 장부 입력과 본인 급여 열람은 후속 확장으로 둔다.

### 가입과 카페 생성

Google 로그인 → 내 카페 목록 → 카페 만들기 → 매장명·시간대 설정 → 소유자 멤버십 생성 → 빈 장부 시작. 참여 카페가 없으면 생성 또는 초대 수락 안내를 제공한다. 파일럿에서는 지정된 사용자만 카페를 생성할 수 있다.

### 초대와 참여

대상 이메일·역할 입력 → 초대 링크 생성 → 초대한 사람이 링크 전달 → 대상자 로그인 → 이메일 확인 → 멤버십 생성. 링크는 7일 후 만료되며 일회용이고 취소할 수 있다. MVP에서는 자동 이메일 발송을 제외한다.

### 카페 전환

상단에서 참여 카페를 선택하면 해당 카페의 권한과 데이터를 조회한다. 모든 장부 화면에 현재 카페명을 표시한다. 미저장 입력이 있으면 전환 전에 확인하고, 이전 카페의 캐시나 늦게 도착한 응답이 섞이지 않게 한다.

### 협업과 동시 수정

활성 화면은 최대 60초 간격으로 갱신하며 화면 복귀·수동 새로고침 시에도 조회한다. 편집 중 입력은 덮어쓰지 않는다. 동일 기록을 두 사람이 수정하면 먼저 저장한 내용을 유지하고, 뒤의 요청에는 충돌 안내와 최신 기록을 제공한다.

## 4 클라우드 구성과 무료 한도

Cloudflare Workers의 정적 파일 호스팅과 API, D1 데이터베이스를 기본안으로 사용한다. Pages의 화면 호스팅 역할을 Workers에 합쳐 배포 구성을 줄인다.

| 구성 요소 | 선택 | 역할 |
| --- | --- | --- |
| 웹 화면 | Workers Static Assets | 기존 화면 배포 |
| 서버 API | Workers | 인증·권한 확인과 데이터 처리 |
| 데이터베이스 | D1 | 계정 연결·멤버십·장부 저장 |
| 로그인 | Google OpenID Connect | 사용자 신원 확인 |
| 서비스 주소 | 제공 기본 도메인 | 도메인 구매 없이 시작 |
| 소스와 배포 | 기존 GitHub 저장소 | 검증 후 운영 배포 |

Google 로그인으로 신원을 확인한 후 서비스 자체 세션을 발급한다. 비밀번호는 직접 보관하지 않는다. 계정 연결은 변경 가능한 이메일 대신 Google의 고유 사용자 ID를 기준으로 한다. 초대 수락에는 검증된 대상 이메일을 사용한다. [4]

### 무료 요금제의 기준

| 항목 | 무료 한도 |
| --- | --- |
| 정적 파일 요청 | 무료·무제한 |
| Workers API 요청 | 하루 100,000회 |
| Workers CPU 실행 시간 | 요청당 10ms |
| D1 읽기 | 하루 500만 행 |
| D1 쓰기 | 하루 100,000행 |
| D1 저장 용량 | DB 하나당 500MB, 계정 전체 5GB |
| D1 시점 복구 | 최근 7일 |

2026년 10월 7일 공식 문서 확인 기준이다. 요금·한도는 배포 전에 재확인한다. D1의 5GB는 계정 전체 한도이며, MVP는 공유 DB 하나를 사용하므로 500MB가 우선적인 저장 한도다. [1–3]

### 무료 운영을 위한 설계

정적 파일은 정적 호스팅 경로로 제공하고 API만 서버에서 처리한다. 페이지 단위 조회와 기간별 집계, 카페·날짜 인덱스로 읽는 행 수를 줄인다. 숨겨진 탭은 갱신을 중지한다. 대량 가져오기는 작은 작업으로 나누고 실제 CPU 사용량을 검증한다.

## 5 데이터 모델과 격리 규칙

공유 DB에서 cafe_id로 카페 데이터를 구분한다. 사용자와 카페는 memberships를 통해 N:N으로 연결한다. 로그인 사용자와 급여 대상 직원은 별도 개념으로 관리한다.

| 테이블 | 주요 내용 |
| --- | --- |
| users | 사용자 ID, 이름, 이메일 |
| auth_identities | 로그인 제공자, 제공자 사용자 ID, 내부 사용자 ID |
| sessions | 세션 토큰 해시, 사용자, 만료 시간 |
| cafes | 카페 ID, 이름, 시간대 |
| memberships | 사용자 ID, 카페 ID, 역할, 상태 |
| invitations | 카페, 대상 이메일, 역할, 토큰 해시, 만료·사용 상태 |
| employees | 카페별 직원 정보, 선택적 사용자 계정 연결 |
| sales / purchases / expenses | 카페별 매출·구매·비용 |
| inventory_items / inventory_movements | 재고 품목과 입출고 기록 |
| work_logs / payroll_settings | 직원별 근무 기록과 급여 설정 |
| audit_logs | 카페, 작업자, 변경 대상·내용·시간 |
| import_jobs | 데이터 가져오기 상태와 중복 확인 |

### 데이터 제약

- memberships의 user_id와 cafe_id 조합은 중복될 수 없다.
- 장부·직원·근무·재고에는 cafe_id가 필수다. 참조하는 직원이나 품목도 같은 카페 소속인지 검증한다.
- 계정 없는 직원도 장부에 등록할 수 있다. 직원에 사용자를 연결할 때 카페 소속을 검증한다.
- 금액은 원 단위 정수로 저장한다. 기록에는 작성자·수정자·시간·버전 번호를 둔다.
- 카페와 날짜를 조합한 인덱스를 설계하고, 집계가 전체 테이블을 불필요하게 읽지 않도록 검증한다.

브라우저 저장소는 테마 등 개인 설정에 사용한다. 클라우드 DB를 장부의 기준으로 삼고, 각 API에서 서버가 멤버십과 역할을 검사한다.

## 6 필수 동작과 기존 자료 이전

| 영역 | 요구사항 |
| --- | --- |
| 데이터 격리 | 모든 API에서 로그인·카페 멤버십·역할을 검증한다. |
| 직접 접근 차단 | 다른 카페 ID나 기록 ID를 넣어도 조회·수정·내보내기가 불가능해야 한다. |
| 권한 회수 | 참여 해제와 역할 변경은 다음 API 요청부터 반영한다. |
| 세션 | HttpOnly·Secure 쿠키, 만료·로그아웃 처리, 변경 요청 위조 방지를 적용한다. |
| 동시 수정 | 버전이 일치할 때만 저장한다. 충돌은 HTTP 409로 반환한다. |
| 중복 저장 | 재시도와 중복 클릭이 같은 거래를 두 번 만들지 않게 한다. |
| 재고 정합성 | 재고 이동과 관련 장부 변경은 함께 성공하거나 함께 실패한다. |
| 저장 실패 | 서버 성공 전에는 완료로 표시하지 않는다. 접속 끊김과 미저장 상태를 알린다. |
| 변경 이력 | 장부 수정·삭제, 멤버십 변경, 가져오기 작업을 기록한다. |

### JSON 자료 이전 절차

1. 사용자가 기존 앱에서 JSON 백업을 내려받는다.
2. 소유자가 새 카페 또는 장부가 비어 있는 카페를 선택한다.
3. 서버가 파일 형식·날짜·금액·직원 연결을 검증한다.
4. 항목별 건수와 합계, 오류를 미리 보여준다.
5. 사용자 확인 후 가져오기를 실행한다.
6. 완료 후 기존 백업과 건수·합계를 비교한다.

MVP에서는 장부가 비어 있는 카페로만 가져오기를 허용한다. 동일 파일의 중복 등록을 차단한다. 큰 파일은 나누어 처리하되, 실패한 작업의 일부 기록이 실제 장부에 노출되지 않게 하고 안전하게 재시도할 수 있어야 한다.

## 7 개발 계획과 출시 검증

개발자 1명 기준 약 4~6주를 초기 추정치로 둔다. 첫 단계에서 기존 코드의 결합도와 급여·재고 계산을 확인한 뒤 일정을 조정한다. 각 단계는 검토 가능한 PR로 나눈다.

| 단계 | 주요 작업 | 완료 기준 |
| --- | --- | --- |
| 1 기존 코드 분석 | 저장 구조·계산 확인, 기능 목록, 샘플 백업 확보 | 이전 대상과 보존 동작 확정 |
| 2 개발과 배포 기반 | 화면·저장 분리, API, D1 스키마, 테스트 환경 | 테스트 주소에서 읽기·쓰기 성공 |
| 3 계정과 권한 | 로그인·세션, N:N 멤버십, 초대·역할 | 두 사용자·두 카페의 권한 격리 |
| 4 공유 장부 | 장부·근무 API 연결, 집계, 충돌 처리 | 여러 기기에서 동일 장부 사용 |
| 5 자료 이전과 운영 | JSON 이전, 내보내기, 이력, 복구·사용량 확인 | 이전 자료 일치, 복구 연습 성공 |
| 6 파일럿 | 실제 카페 1~2개 운영, 오류 수정 | 출시 기준 충족 후 이용 확대 |

테스트용 DB와 운영 DB를 분리한다. 미리보기 배포는 운영 장부에 접근하지 않는다.

### 파일럿 시작 전 통과 기준

- 사용자 A가 카페 1의 소유자, 카페 2의 직원으로 서로 다른 권한을 가진다.
- 참여하지 않은 카페는 모든 API에서 읽기·변경이 차단된다. 직원에게 전체 손익과 다른 직원의 급여가 응답으로 전달되지 않는다.
- 만료·취소·사용된 초대를 재사용할 수 없다. 동시 수락에도 멤버십은 하나만 생성된다.
- 동시 수정으로 조용히 덮어쓰지 않는다. 중복 요청으로 거래나 재고 이동이 중복 생성되지 않는다.
- 카페 전환 후 이전 카페의 데이터가 나타나지 않는다.
- JSON 이전 전후 항목 수와 합계가 일치하며 실패한 이전을 안전하게 재시도한다.
- 백업 복구 후 카페별 데이터와 권한이 유지된다.
- 동시 접속 10명에서 주요 조회·저장 응답의 95%가 2초 이내를 목표로 한다.

## 8 운영 기준과 착수 결정

무료 운영은 사용자 수보다 요청 수, DB가 읽는 행 수, 저장량에 영향을 받는다. 실제 사용량을 확인한 뒤 이용 범위를 확대한다.

### 사용량과 오류 관리

- 일별 요청·읽기·쓰기 사용량과 DB 크기를 확인한다. 로그에 장부 원문·세션 토큰·초대 토큰을 남기지 않는다.
- 한도 70%에서 최적화를 검토하고, 85%에서 확대 운영 중단 또는 유료 전환을 검토한다.
- 한도 초과로 요청이 실패하면 저장 실패를 알리고 무한 재시도를 막는다.

### 백업과 복구

D1 시점 복구와 카페별 JSON 내보내기를 함께 사용한다. 파일럿에서는 소유자가 매일 백업을 내려받고, 정기 외부 백업 자동화는 다음 단계로 진행한다. 공유 DB 전체 복구는 다른 카페에도 영향을 주므로 개별 카페 복구 절차도 검증한다.

### 초기 결정안

| 항목 | 기본안 |
| --- | --- |
| 로그인과 카페 생성 | Google 로그인만 지원, 파일럿 지정 사용자만 카페 생성 |
| 소유자와 관리자 | 카페당 소유자 1명, 관리자는 전체 장부·급여 접근 |
| 직원 | 본인 근무 기록만 접근 |
| 초대 | 대상 이메일에 연결된 일회용 링크 |
| 협업 반영 | 수동 새로고침과 활성 화면 60초 갱신 |
| 데이터 이전 | 빈 카페에만 JSON 가져오기 |
| 배포 | 무료 기본 도메인, 테스트·운영 분리 |

착수에는 Cloudflare 계정, GitHub 배포 연결, Google 로그인용 OAuth 앱 설정이 필요하다. 첫 개발 목표는 두 사용자가 두 카페에 서로 다른 권한으로 참여하고 매출 한 건을 안전하게 공유하는 흐름이다.
